# SLMによる「もしかして」の評価結果（2026-09-26）

IME本体でSLM（小型言語モデル）を使うかどうかを決めるために行った比較テスト（テスト計画書 T-S06）の結果と判断を記録する。

## 判断

- **IME本体ではSLMを使わない。SLMをパッケージに含めるオプションも用意しない。** もしかして（B-14）や文脈の判断は、辞書とアルゴリズムで実装する
- SLMは、開発時の辞書作成環境（計画書 4.5.1）で、トークン数を減らすための部品として使う。この方針は変えない
- 理由: どのモデルも、SLMを使わないアルゴリズムを明確には上回らず、正しく入力した読みへの誤った提案が増えた。さらに1回あたり0.6〜2.8秒のCPU時間と0.8〜2.9GBのメモリが必要で、CPU・メモリ・バッテリーへの負荷が大きい

## 負荷の見積もり

最も軽い sarashina2.2-0.5b Q4_K_M でも、1回あたり約0.6秒のCPU時間と約1GBのメモリが必要だった。候補がある語のたびに呼ぶと（今回のコーパスでは69%）、入力のたびにCPUが動き続け、ノートPCではバッテリーへの影響が大きい。アルゴリズムは1語あたり2ms以下で、常に動かしても負荷は無視できる。

## アルゴリズムが外した例と次の改善

| 種類 | 例 | 改善の方向 |
| --- | --- | --- |
| 打った読みも語になる | しちょう→資料、ひかん→時間、こーじー→コーヒー | 前の文脈との連接コスト・共起で判断する |
| 活用の断片が候補に混じる | だんしゃ→出しゃ、れんらこ→連だこ | 候補を名詞などの自立した語に絞る |
| 1キーの修正では届かない | すまーとほん→スマートフォン、いんたーねっろ→インターネット | よくある打ち間違いの規則（f/h、ローマ字のゆれ）と、2キー以内の修正を加える |

打ち間違いのコーパスを増やし、よくあるケースをアルゴリズムで直せるようにする。比較の仕組みは手動で実行できるように残す（`workflow_dispatch`）。

## アルゴリズムの改善（2026-09-26）

判断のあと、SLMを使わずに次の規則を加えた（`core/src/typo_candidates.cpp`、`SuggestTypoCorrection`）。

- 候補を自立語だけにする（助詞・活用語尾などを除く）
- よくある打ち間違いを安く扱う: 母音・ーの二度押し（`kaigii`）、長音の抜け（`ryoko`→`ryokou`、`sense`→`sensei`）
- 新しい修正の種類: 母音の打ち間違い（`dansya`→電車）、似た音のキー（h/f、j/z、v/b）、促音の2キー（`nerro`→`netto`）、んの抜け（`konichiha`→こんにちは）
- ローマ字であまり使わないキー（ch以外のc、q、x、l）を使う修正は高くする
- 前の語との連接コストを使い、打った読みが語のときは候補が500以上自然な場合だけ出す（余裕の値は下の比較で選んだ）

コーパスは打ち間違い102件・正しい読み58件に増やし、辞書のよく使う語500語も誤提案の確認に使う（`eval/typo/typo.tsv`、テスト計画書 T-B14-4）。CIで毎回測り、`eval/typo-baseline.tsv` より悪くなると失敗にする。

## 機械的に入れた打ち間違いでの計測（2026-09-26）

手で書いた文例だけでは件数が少ないので、辞書のよく使う語（漢字を含む名詞）に打ち間違いを1つずつ機械的に入れて、元の読みに戻るかを測った（`astelio_typo --synthetic 400`、固定の乱数で毎回同じ）。文例も打ち間違い130件・正しい読み78件に増やした。

| 項目 | 結果 |
| --- | ---: |
| 文例の的中率 | 82.3%（107/130） |
| 正しい読み・よく使う語への誤提案率 | 0.0% / 0.0% |
| 機械的な打ち間違いの的中率 | 83.9%（296/353） |
| 　隣のキー | 92.1% |
| 　キーの抜け | 54.5% |
| 　余分なキー | 97.7% |
| 　入れ替わり | 90.9% |

キーの抜けが低いのは、抜けた読みも語になることが多いため（`jibun`→`ibun` 異聞、`kinou`→`kino` 紀、`heiwa`→`hiwa` 秘話）。打った読みが語のときに出しすぎると、正しく打った語にも誤提案が出るので、ここは入力の履歴で補う。基準値は `eval/typo-baseline.tsv`。
