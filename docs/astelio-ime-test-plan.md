# Astelio IME テスト計画

開発計画（[astelio-ime-plan.md](astelio-ime-plan.md)）の要件ID（R / B / C / D）に対応するテストを定める。

## 1. 目的と方針

- すべての要件に、少なくとも1つの自動テストを対応させる
- 手動でしか確認できない項目（候補ウィンドウの見た目、アプリごとの挙動差）は、チェックリストでリリースごとに確認する
- これまでに起きた不具合は、再発防止テストとして必ず自動化する（6章）
- 変換精度と性能は数値で測り、前回より悪化したらCIを失敗させる

## 2. テストの種類

| 種類 | 対象 | ツール | 実行タイミング |
| --- | --- | --- | --- |
| 単体テスト | Core（ローマ字変換、記号ルール、単押し判定、辞書、変換、学習） | GoogleTest | PRごと |
| 変換精度テスト | Core + システム辞書 + 補強辞書 | 独自の評価ツール（`eval/`） | PRごと（抜粋）、毎晩（全件） |
| 性能テスト | キー処理、変換、予測、起動 | Google Benchmark、ETW（Windows）、signpost（macOS） | PRごと（簡易）、毎晩（全件） |
| ファジング | ローマ字変換、辞書読み込み、IPCメッセージ | libFuzzer + AddressSanitizer | 毎晩（各1時間） |
| 結合テスト（サーバー） | IPC、セッション、再起動、学習の共有 | GoogleTest + テスト用クライアント | PRごと |
| 結合テスト（Windows TIP） | TSF上のキー処理、未確定表示、確定 | テスト用ホストアプリ（3.3） | PRごと |
| 結合テスト（macOS） | IMKInputController | XCTest + 模擬クライアント | PRごと |
| UIテスト | 設定アプリ、候補ウィンドウ、実アプリでの入力 | FlaUI（Windows）、XCUITest（macOS） | 毎晩 |
| インストーラーテスト | 導入、更新、削除 | PowerShell + 仮想マシン | リリース前 |
| 互換性テスト | 主要アプリでの入力 | チェックリスト（8章） | リリース前 |
| セキュリティ・プライバシーテスト | IPCの権限、通信の有無、学習データの削除 | 独自スクリプト + ファジング | 毎晩、リリース前 |

## 3. テスト環境

### 3.1 端末

| ID | OS | CPU | 用途 |
| --- | --- | --- | --- |
| ENV-W1 | Windows 11 ARM64 | Snapdragon X系 | 主な開発・性能測定。x64エミュレーションと32bitアプリの確認 |
| ENV-W2 | Windows 11 x64 | Intel Core Ultra系 | x64ネイティブの確認 |
| ENV-W3 | Windows 11 x64 | AMD Ryzen系 | x64ネイティブの確認（CIでも可） |

- キーボードは英語配列（US ANSI）のみ。OSのキーボード設定も英語配列にする
- 日本語配列のキーボードをつないだ場合は「対象外」として動作が壊れないこと（入力できなくても落ちないこと）だけを確認する

### 3.2 CI

| ランナー | 実行内容 |
| --- | --- |
| Windows ARM64（`windows-11-arm`） | ビルド（ARM64）、単体、.NET、精度（抜粋）、TIP結合、性能（簡易） |
| Windows x64（`windows-latest`） | ビルド（x64 / x86）、単体、.NET、TIP結合 |
| macOS arm64（`macos-latest`） | ビルド（Universal 2）、単体、XCTest |
| macOS x86_64（`macos-15-intel`） | Universal 2のx86_64部分での単体 |
| Linux x64（`ubuntu-latest`） | Coreのファジング（clang + libFuzzer + ASan/UBSan。CoreはOSに依存しないためLinuxで行う） |

- ランナー名はGitHubのドキュメント（GitHub-hosted runners reference、2026-09-24確認）による。公開リポジトリでは無料で使える
- ワークフローは [.github/workflows/ci.yml](../.github/workflows/ci.yml)。PRと `main` への反映で実行する

### 3.3 Windows TIPのテスト用ホスト

実アプリでの入力は結果の取得が不安定なため、TIPの結合テストには専用のホストアプリを使う。

- テスト用ホストは独自の `ITextStoreACP` を実装し、未確定文字列・下線・カーソル位置・確定文字列をすべて記録する
- キー入力は `ITfKeystrokeMgr::TestKeyDown` / `KeyDown` / `KeyUp` でTIPに直接渡す（OSの入力経路やフォーカスに左右されない）
- 実キー経路（`SendInput`）での確認は、別プロセスから送る方式でUIテストとして行う
- メニューの起動は、ホストのウィンドウで `WM_SYSCOMMAND`（`SC_KEYMENU`）の受信回数を数えて確認する
- ARM64 / x64 / x86 の3種類のホストを用意し、それぞれ同じアーキテクチャのTIPを読み込ませる
- TIPの登録（HKCR / HKLMへの書き込み）は管理者権限が必要なため、登録を伴う結合テストは環境変数 `ASTELIO_TIP_INTEGRATION=1` のときだけ実行する。GitHubのWindowsランナーは管理者で動くため、CIでは常に実行する

### 3.4 macOSのテスト用クライアント

- `IMKTextInput` を実装した模擬クライアントを作り、`handle(_:client:)` にキーイベントを渡して、未確定文字列（`setMarkedText`）と確定文字列（`insertText`）を記録する
- 実アプリでの確認はXCUITestでテキストエディットを操作する（アクセシビリティの権限が必要）

## 4. 要件ごとのテストケース

「自動」はCIで実行する。「手動」はチェックリストで確認する。

日本語モードでの英字入力は次の仕様（フェーズ1で確定）。Shiftを押しながら英字を打つと一時英数になり、以降の英字・数字・記号はローマ字変換せずに未確定のまま入る。一時英数は、確定・取り消し・Shiftの単押しで終わる。

### 4.5 言語モデルによる辞書の補強

辞書補強は人が介在しないため、すべて自動テストとする。AIの応答は模擬モデル（決められた応答を返すテスト用のサーバー）で再現し、実モデルでの実行は毎晩行う。

| ID | テスト内容 | 期待結果 | 方式 |
| --- | --- | --- | --- |
| T-A01 | 読みと表記が明らかに合わない生成結果（例: 表記 `東京`、読み `おおさか`）を検証に通す | 規則による検証で除外され、評価AIには回らない | 自動 |
| T-A02 | 生成AIと照合AIの結果が一致し、確信度が高い語 | 評価AIを通らずに採用候補になる | 自動 |
| T-A03 | 生成AIと照合AIの結果が一致しない語 | 評価AIに回される | 自動 |
| T-A04 | 評価AIが「採用」「却下」「修正案」を返す | それぞれ採用候補・不採用・再検証に進む | 自動 |
| T-A05 | 評価AIの修正案が再検証でも確信度が低い | 2回目の修正は行わず却下される（処理が繰り返しにならない） | 自動 |
| T-A06 | 評価AIが形式の崩れた応答、空の応答を返す。応答が時間内に返らない | 却下扱いになり、処理全体は止まらない | 自動 |
| T-A07 | 評価AIに渡す最初の問い合わせ | 生成AI・照合AIの結果が含まれていない（目印なしの判定になっている） | 自動 |
| T-A08 | 確認用の語を混入させて実行する | 確認用の語は影響を受けず、補強辞書に入らない。各AIの正解率が記録される | 自動 |
| T-A09 | 模擬モデルで評価AIの正解率を基準未満にする（生成AI・照合AIも同様に確認） | その回の結果がすべて不採用になり、処理が止まる | 自動 |
| T-A10 | 確認用の語で測った誤り率からしきい値を調整する | 調整後の誤り率が目標（初期値 1%）以下になる | 自動 |
| T-A11 | 使うモデルの版を変える | しきい値の再調整が終わるまで採用されない | 自動 |
| T-A12 | 補強辞書の有無で評価コーパスを実行する | 正解率が下がる場合は採用されない | 自動 |
| T-A13 | 採用後に正解率が下がる状況を作る | 該当する回の追加分だけが自動で取り消される | 自動 |
| T-A14 | 処理を途中で強制終了して再実行する | 途中から再開し、同じ語が二重に登録されない | 自動 |
| T-A15 | 同じ入力と設定で2回実行する | 同じ結果になる | 自動 |
| T-A16 | 補強辞書の各語 | モデルの名前・版・ハッシュ、確信度、各AIの判定と理由が記録されている | 自動 |

### 5.2 進め方

- 同じ入力データ（評価コーパスの読み）を毎回使う
- 各項目を1,000回以上測り、p50 / p95 / p99を記録する

- CIでは前回の値と比べ、p95が10%以上悪化したら失敗にする。実機（ENV-W1 / ENV-M1）での測定は毎週行う

## 12. 不具合の管理

| 重大度 | 基準 | 対応 |
| --- | --- | --- |
| S1 | 入力先アプリが落ちる、入力できなくなる、データが消える、入力内容が漏れる | すぐに修正する。リリースを止める |
| S2 | 主要な機能が使えない（変換できない、モード切替が効かない） | リリース前に修正する |
| S3 | 一部のアプリや条件でだけ起きる、回避策がある | 次の版までに修正する |
| S4 | 表示の乱れなど軽微なもの | 優先度を決めて対応する |

- 不具合を直すときは、先にその不具合を再現するテストを書く
- 修正後、そのテストを6章の再発防止テストに追加する
